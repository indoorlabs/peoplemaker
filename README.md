# PeopleMaker

공간에 **사람**을 넣는다. spacemaker 가 공간을 만들고, 이쪽이 그 안에 살 사람을
만든다.

```
indoorlabs/spacemaker    건물 공간 · BIM · 디지털트윈
indoorlabs/urbanspace    도시 스케일 · 보행 · 교통
indoorlabs/peoplemaker   ← 여기. 위 둘이 함께 쓴다.
```

## 무엇을 하고, 무엇을 하지 않는가

**한다** — 사람의 몸(인체치수·아바타)과 동작(모션 클립)을 만들어 **자산으로
내보낸다**. 텍스트→동작 생성, 영상→모션 캡처, 리타게팅, 라이선스 기록.
"회의하기·대피하기" 같은 상위 명령을 **동작의 차례**로 푸는 것까지 (활동).

**안 한다** — 그 사람을 **어디에 놓을지**는 안 정한다. 배치·동선·활동
스케줄은 공간을 아는 쪽(spacemaker · urbanspace)의 일이다. 여기서 그것까지
하면 두 저장소가 같은 것을 두 벌 갖게 되고, 한쪽만 고쳐진다.
회의도 마찬가지다 — **몸이 무엇을 하는가**는 여기, **어느 방에서 언제 누구와**
는 공간 쪽이다.

경계는 **계약** 하나다:

```
PeopleMaker  ──[ Motion Asset Pack ]──>  spacemaker / urbanspace
             catalog.json + body.glb + clips/*.glb
             (몸은 한 번 · 동작 파일에는 뼈 움직임만)
```

계약이 지켜지는 한 이 안에서 몸 모델을 바꾸든 생성기를 바꾸든 소비하는 쪽은
안 바뀐다. **그 갈아 끼우기가 이 저장소가 따로 있는 이유다** — 2026년 2월
Epic 이 Meshcapade(SMPL 상업 라이선스 창구)를 인수하면서, 몸 모델 하나가
제품 전체를 물고 갈 수 있다는 것이 분명해졌다.

## 규약

이 저장소는 urbanspace 의 규약을 그대로 쓴다. 요점 셋:

1. **순수 층** — `src/lib/*.mjs` 는 three.js·DOM·PyTorch 를 import 하지
   않는다. 값과 규칙만 있고, 그래서 게이트가 브라우저 없이 검사한다.
   (`check-purity` 가 지킨다 — three 를 **막아 놓고** 순수 층을 통째로 불러 본다.)
2. **값 옆에 손으로 베낀 수를 두지 않는다** — 인체치수든 라이선스든 **출처**가
   함께 있어야 하고, 없으면 게이트가 막는다.
3. **게이트가 기본** — `scripts/check-*.mjs` 를 쓰면 그 순간부터 검사된다
   (등록 단계 없음). 새로 생긴 결함만 빌드를 막는다.

```
npm i                      게이트가 three 를 쓴다 (재생기 검사용, devDependency)
npm run check              전부 검사
npm run check -- --update  기준선 재잠금
```

`src/lib` 는 의존성이 없다. three 를 쓰는 것은 `src/web` 과 그 게이트뿐이고,
그것도 **import 하지 않고 주입받는다** — 소비처가 이미 three 를 쓰고 있어서,
이 저장소가 제 판을 끌어오면 한 페이지에 two 벌이 뜬다.

## spacemaker · urbanspace 에서 쓰는 법

```bash
npm i github:indoorlabs/peoplemaker
```

three 는 **peer 의존**이다 — 소비처가 이미 쓰는 판을 그대로 쓴다. 이
저장소가 제 판을 끌어오면 한 페이지에 두 벌이 뜬다.

밖에서 보는 문은 **`src/web/index.mjs` 하나**이고, 패키지의 진입점이 그것을
가리킨다 (`import { loadPack } from 'peoplemaker'`). 순수 층만 필요하면
`peoplemaker/lib` 로 들어온다 — three 가 안 딸려 온다. 안쪽 파일을 직접
가져가면 내부를 고칠 때마다 남의 저장소가 깨진다 — 게이트가 그 문의 목록을
지킨다.

three 는 **주입한다.** 소비처가 이미 쓰고 있는 판을 그대로 넘긴다 (이
저장소가 제 판을 끌어오면 한 페이지에 두 벌이 뜬다).

```js
import * as THREE from 'three';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import * as SkeletonUtils from 'three/addons/utils/SkeletonUtils.js';
import {
  loadPack, bakeFromPack, geometryOf,
  createClipPlayer, createInstancedCrowd, createMixedCrowd, planCrowd,
  measuredFor, planCrowdMeasured,
} from 'peoplemaker';

// 1. 팩을 받는다. 계약을 어긴 팩은 **여기서** 던진다.
//    팩 파일은 앱이 서비스하는 주소에 둔다 (node_modules 의 packs/ 를
//    복사하거나, 따로 배포한 팩을 가리킨다).
//    동작은 필요한 것만 받을 수 있다 — 나머지는 나중에 pack.load(['talk']).
//    (Rocketbox 한 사람: 몸 4MB + 걷기·서기 0.2MB. 동작을 다 받으면 8~11MB.)
const pack = await loadPack({
  url: '/packs/ref-synthetic', GLTFLoader,
  clips: (cat) => cat.clips.filter((c) => c.rootMotion === 'travel' || c.id === 'idle').map((c) => c.id),
});

// 2. 몇 명을 어느 단계로 세울지 — 예산이 정한다 (한 프레임 4ms 기준)
//    진짜 몸으로 잰 표가 있는 팩(Rocketbox)은 그 표로 센다. 뼈 수로 세는
//    planCrowd 는 그 몸을 13~15배 싸게 본다 (lib/crowdBudget.mjs 의 PACK_MEASURED).
//    몸을 몇 가지 섞는지도 값이다 — 팩마다 군중이 하나씩 생긴다 (kinds).
const table = measuredFor(pack.catalog.packId);
const plan = table
  ? planCrowdMeasured(want, 4, table, ['full', 'instancedLod'], { kinds: packs.length })
  : planCrowd(want, 4, ['full', 'instanced']);

// 3. 가까운 사람 — 사람마다 스킨 메시
const player = createClipPlayer({ THREE, SkeletonUtils, catalog: pack.catalog, gltfOf: pack.gltfOf });
const p = player.spawn({ clipId: 'walk-forward', position: [x, 0, z], headingRad: h });
const pick = player.walkAt(p, 1.1);   // 원하는 속도 → 클립과 재생 속도를 골라 준다

// 경로를 따라 직접 옮길 거라면 클립은 제자리로 두고, **pick.effectiveMps 로**
// 옮긴다. 다른 속도로 옮기면 발이 미끄러진다.
const q = player.spawn({ clipId: 'walk-forward', inPlace: true });
player.placeAt(q, [x, 0, z], headingRad);   // 프레임마다

// 4. 먼 사람 — 구운 자세, 드로우콜 하나. 살은 줄이고 색은 구워서 준다.
//    뼈와 가중치는 안 건드리므로 **같은 아틀라스를 그대로 쓴다**.
//    Rocketbox 몸에서 삼각형 8,064 → 2,016 · 1,000명이 4.81 → 1.46ms.
//    color 를 주면 팩의 텍스처를 정점 색으로 굽는다 (안 주면 다 같은 회색).
const atlas = bakeFromPack(pack);
const geom = geometryOf(pack, { lod: 0.25, color: true });
const crowd = createInstancedCrowd({ THREE, geometry: geom, atlas, count: n });
crowd.place(i, { position: [x, 0, z], headingRad: h, clipId: 'walk-forward' });

// 4-2. 몸이 여럿이면 — 팩마다 군중 하나, 사람 번호는 이어진다
//      (한 팩이 한 사람이라, 안 섞으면 먼 군중이 같은 사람 수천 명이다)
const mixed = createMixedCrowd({
  THREE, count: n,
  kinds: packs.map((p) => ({ id: p.catalog.packId, atlas: bakeFromPack(p), geometry: geometryOf(p, { lod: 0.25, color: true }) })),
  // 누구를 어느 몸으로 할지는 **쓰는 쪽이 정한다**. 안 주면 고르게 섞는다.
});
for (const m of mixed.meshes) scene.add(m);
mixed.place(i, { position: [x, 0, z], headingRad: h, clipId: 'walk-forward' });

// 5. 프레임마다
player.update(dt);
crowd.update(dt);
```

**배치·경로·활동 스케줄은 이 저장소가 안 한다** — 공간을 아는 쪽의 일이다.
여기서 주는 것은 "이 사람이 지금 어떤 자세인가" 와 "몇 명까지 감당되는가" 다.

### 먼 사람의 살 줄이기 (LOD)

드로우콜을 하나로 줄이고 나니 **벽이 정점으로 옮겨 갔다.** 드로우콜이 2 인데
1,000명이 4.81ms 였고, 그러면 남은 것은 삼각형 몫뿐이다. 이차오차(QEM)로
모서리를 접어 살을 줄인다.

```
Rocketbox 여자 01 · 먼 단계 · 같은 기계 (2026-09-12)

                  삼각형   200명   1,000명   5,000명
  안 줄임          8,064   1.46ms   4.81ms      —
  줄임 (0.25)      2,016   0.95ms   1.46ms   5.32ms
  줄임 (0.1)         806      —        —     2.46ms

  4ms 예산에 823명 → 3,623명
```

대가는 살이 원래에서 벗어나는 거리다. 0.25 에서 **최대 17.3mm · 평균
1.62mm** (키 1.74m 인 몸에서), 0.1 이면 최대 44.9mm 로 커진다. 이 수는 기계를
안 타는 **이 살의 성질**이라, 게이트가 매번 다시 재서 기록과 견준다.

**뼈도 가중치도 안 건드린다** — 접을 때 두 점 중 하나를 남기고 그 점의 것을
그대로 쓴다 (새 점을 지어내면 가중치를 섞어야 하고, 어깨와 팔의 가중치를
섞으면 그 정점이 어느 쪽도 아닌 데로 끌려간다). 그래서 구운 아틀라스가
그대로 맞는다.

줄이는 데 브라우저에서 74ms 가 든다 (Rocketbox 몸). 첫 화면에서 한 번이다.
게이트: `scripts/check-lod.mjs`.

### 먼 사람용 몸을 팩이 굽는다 (`body-far.glb`)

줄이기와 색 굽기를 **받는 쪽 브라우저에서 매번** 하고 있었다 (130ms). 그런데
그 결과는 팩마다 늘 같다 — 구울 때 한 번 만들어 넣으면 된다.

```
같은 화면 (1,000명 · 줄인 살 · 구운 색) 을 두 길로

  몸째 받아 브라우저에서 줄이기   4,480KB · 준비 101ms · GPU 1.47ms
  팩이 구워 둔 먼 몸을 받기         337KB · 준비   0ms · GPU 1.51ms

  몸 파일만 보면 4,238KB → 95KB (2.2%)
```

먼 몸은 **단계가 둘**이다. 더 멀면 더 줄인다:

```
             삼각형   파일    200명   1,000명   10,000명   벗어남(최대)
  0.25       2,016    95KB    0.95      1.46        —        17.3mm
  0.1          806    52KB    0.65      1.35      4.77       44.9mm

  4ms 예산: 3,623명 → 8,327명
```

0.25 짜리를 **다시 줄여 쓰지 않는다** — 재 보니 두 번 줄인 쪽이 17% 더
벗어났다 (52.7 vs 44.9mm · 평균 7.00 vs 5.25mm). 늘 원래 몸에서 줄인다.

```js
const pack = await loadPack({ url, GLTFLoader, body: 'far', farRatio: 0.1 });
pack.farLevel   // { file, ratio, vertices, triangles, from } — 무엇을 받았는지
```

먼 몸에는 **텍스처가 없다** (색은 정점에). 도시 스케일 화면은 1024×1024 PNG
셋을 한 번도 안 쓰면서 받고 있었던 것이다.

```js
// 먼 사람만 세우는 화면
const pack = await loadPack({ url, GLTFLoader, body: 'far' });
const geom = geometryOf(pack);      // 이미 줄이고 색까지 구운 살이다
```

뼈·skin·역바인드는 몸의 것을 그대로 쓰므로 **같은 동작 파일과 같은 구운
아틀라스가 그대로 맞는다**. 가까운 사람에게는 안 쓴다 (살이 4분의 1이고
텍스처가 없다). 먼 몸이 없는 팩에 `body: 'far'` 를 달라고 하면 **말하고
멈춘다** — 조용히 몸째를 주면 받는 쪽은 95KB 를 기대하고 4MB 를 받는다.

굽는 길은 한 군데다: `node scripts/build-far.mjs --all`.

### 먼 사람의 색

먼 단계는 한 색으로 칠했다 — 100명을 세우면 100명이 같은 회색 덩어리였다.
이제 팩의 baseColorTexture 를 UV 로 찍어 **정점마다 색 하나**를 굽는다
(`geometryOf(pack, { color: true })`).

텍스처를 그대로 쓰지 않는 까닭은 값이다. 1024×1024 PNG 셋이 3.7MB 이고,
화면에서 몇 픽셀인 사람에게 그 해상도는 통째로 버려진다. 정점 색은 정점마다
12바이트라 줄인 살(정점 1,030)에서 **12KB** 다. 드로우콜도 재료도 안 는다.

```
1,000명   4.81ms(안 줄임) → 1.46ms(줄임) → 1.37ms(줄임 + 색)
5,000명                      5.32ms         5.57ms
```

값이 오르내리는 폭이 재기의 흔들림과 같은 자릿수다 — **색은 사실상 공짜다.**
굽는 데 브라우저에서 130ms (줄이기 74ms + 그림 풀기·찍기 56ms).

멀리서 눈에 남는 것은 무늬가 아니라 덩어리 색이다 — 남색 웃옷·살색 팔·검은
머리. 그것은 정점 색으로 남는다. 텍스처가 없는 팩은 baseColorFactor 로
물러서고, 둘 다 없으면 색이 없다고 말한다 — 그럴듯한 살색을 지어내지 않는다.

게이트: `scripts/check-color.mjs` — 아는 그림에서 아는 색이 나오는가, **v 가
아래로 가는가**, 줄여도 그 색이 원래 있던 색인가, 진짜 몸에서 색이 정말
여럿인가(흩어짐 0.199 · 141가지 · 부위마다 다른가).

### 사람마다 다른 사람 (팩 섞기)

한 팩은 한 사람이다 (그 규약은 의도한 것이다 — 두 사람을 한 팩에 넣으면
속도에 맞춰 클립을 고르다 걷는 도중에 사람이 바뀐다). 그래서 먼 군중이
**같은 사람 수천 명**이었다.

먼 단계는 InstancedMesh 하나이고, 인스턴스들이 **같은 기하를 나눠 쓰는 것**이
드로우콜을 줄인 방법 자체다. 그러니 한 군중에 몸 둘을 넣을 길이 없다 —
몸마다 군중을 둔다. `createMixedCrowd` 가 사람 번호를 (어느 몸, 몇 번째)로
옮겨 주고, 쓰는 쪽은 몸이 몇이든 `place(i, …)` 하나로 본다.

```
같은 기계 · 줄인 살 · 구운 색 (2026-09-12)

   사람    몸 하나   몸 둘   몸 여섯
    200     0.95     1.00     1.16
  1,000     1.37     1.52     1.93
  5,000     5.57     5.23     5.56
  드로우콜    2        3        7

  4ms 예산:  3,623명 · 3,671명 · 3,284명
```

**몸 가짓수는 고정비로 들어온다** — 200명에서 몸 하나당 0.04ms 다. 사람 수에
붙는 값이 아니라 시작할 때 한 번 치르는 값이고(드로우콜과 버퍼 바꿔 끼우기),
그래서 여섯으로 늘려도 예산 안 사람이 9% 준다. 둘일 때 오히려 는 것은 남자
01 의 줄인 살(삼각형 1,748)이 여자 01(2,016)보다 가볍기 때문이다 — 값은 사람
수가 아니라 **삼각형**을 따라간다.

몸 둘을 한 기하에 이어 붙이고 안 쓰는 쪽을 찌그러뜨리는 길은 안 간다 —
그러면 **모든 사람이 모든 몸의 정점 값을 치른다** (5,000명 × 몸 둘 = 정점
두 배). 드로우콜 하나 아끼자고 삼각형을 두 배로 그리는 셈이다.

지금 팩은 여덟이다 — 여자 01·02, 남자 01·02, 정장 여자·남자 01, **남자아이
01 · 여자아이 01**. 한 사람 받는 데 3분쯤 걸리고(내려받기가 대부분), 팩이
8~12MB · 원본 캐시가 따로 528MB 다. 더 늘리려면 `PRESETS` 에 한 줄 적고
스크립트를 돌린다:

```sh
node scripts/import-rocketbox.mjs rocketbox-f03
```

게이트: `scripts/check-mix.mjs` — i 번을 놓으면 **그 몸의 그 칸**만 움직이는가,
옮기기가 재생 시각을 안 건드리는가, 없는 클립·없는 사람을 말하고 막는가,
그리고 잰 표가 **몇 가지로 잰 것인지** 말하는가 (여섯으로 잰 표를 스무
가지에 슬쩍 쓰면 예산이 거짓말한다).

### 인체치수를 받았다 — 사이즈코리아 제8차 (`anthropometry.mjs`)

P0 부터 `pending` 이던 다섯 치수가 채워졌다. 포털(sizekorea.kr)이 이 기계에서
계속 안 열렸는데 2026-09-13 에 열렸고, 그날 받았다.

```
제8차 한국인 인체치수조사 (국가기술표준원, 2020~2023) · 20~69세
남 n=4,295 · 여 n=5,285 · 단위 mm

                      남 평균    남 p5     남 p95    여 평균    여 p5     여 p95
  키                  1731.91   1628     1832.14   1603.67   1516     1697
  눈높이               1606.2    1507.24  1702.74   1483.98   1400.03  1572
  어깨사이길이           446.68    406.08   488       400.53    365      436.07
  앉은키                934.73    882      986       875.79    827      926
  가슴두께               232.51    199.96   268       207.41    171.26   250.47
  앉은눈높이             807.65    757      858       755.03    709.13   802
```

**평균만 두지 않는다.** 5·50·95 백분위를 함께 둔 까닭은 쓰임이 다르기
때문이다 — 통행 폭은 95, 손이 닿는 높이는 5 를 쓴다. 평균 하나만 두면 쓰는
쪽이 반쪽에게 모자란 문을 낸다. **표본 수(n)도 값의 일부다**: 4,295명과
40명은 같은 95 백분위가 아니다.

받은 길도 함께 적는다 (`SOURCES.sizekorea8.api`) — 항목 코드와 POST 형식이
있어서 같은 수를 다시 물을 수 있다. 포털이 다시 닫힐 수 있는 값이라 더 그렇다.

#### 옛 값이 틀렸다

전에 적혀 있던 키 1725(남) · 1596(여)는 보도자료에서 옮긴 값이었는데,
**포털에서 재현되지 않는다**. 8차 20~69세는 1731.91 · 1603.67 이고, 20~59세로
좁히면 1741.42 다. 어느 범위를 쓴 수였는지 알 수 없어 포털 값으로 바꾸고,
모집단 이름도 `kr-male-adult` → `kr-male-20-69` 로 고쳤다 — **20~69세만 잰
조사를 "한국인" 으로 읽으면 어린이 치수가 조용히 어른 값이 된다.**

#### 다섯이 채워지자 더 좁은 두 구멍이 드러났다

```
childBodyDims   제8차는 20~69세만 잰다 — 7~12·13~18세를 물으면 0명이 나온다.
                학교 프로필이 어린이 팩을 세우므로 이 값이 필요하다
buttockFlesh    앉았을 때 엉덩이 살 두께가 측정 항목에 아예 없다.
                팩의 seat 은 엉덩이 **뼈** 높이라, 의자 **면**의 높이를
                내려면 이 값이 있어야 한다
```

#### 그리고 팩의 몸이 어디쯤인지 처음으로 알게 됐다

```
한국 20~69세 키 분포에서 (p5 ~ p95)

  남자 01     1.810m   안    (1.628 ~ 1.832)
  남자 02     1.806m   안
  정장 남 01  1.801m   안
  여자 01     1.741m   밖 ▲  (1.516 ~ 1.697)
  여자 02     1.732m   밖 ▲
  정장 여 01  1.732m   밖 ▲
```

**여자 팩 셋이 전부 한국 여자 95 백분위보다 크다.** Rocketbox 는 서양
아바타이니 결함은 아니다 — 다만 모르고 쓰면 한국 학교 복도를 서양 사람으로
검토하게 된다. 게이트가 이것을 적어 두고 바뀌면 말한다.

**폭은 견주지 않는다.** 팩의 `maxWidthM`(0.586m)은 팔을 포함한 경계상자
너비이고, 사이즈코리아의 어깨사이길이(0.4467m)는 어깨점 사이 거리다 — 다른
것을 재고 있어서 이 둘을 견주면 안 된다.

게이트: `scripts/check-anthropometry.mjs` — 검사가 18 → 391 이 됐다. 값이
늘면 검사도 함께 는다: 백분위 차례(5<50<95)가 맞는가, 평균과 중앙값이
벌어지지 않는가(다른 모집단이 섞인 자리다), 한 항목 안에서 표본 수가
갈리지 않는가, 앉은키가 키보다 작은가. 다섯 군데를 일부러 깨서 확인했다 —
그중 "p5 자리에 p95 를 넣기"(열 밀림)는 **백분위 차례 검사만** 잡는다.

### 몸을 재서 계약에 넣는다 (`bodyDims`)

공간 쪽이 복도 폭과 창 높이를 검토하려면 **이 사람이 얼마나 넓고 눈이 어디에
있는지**를 알아야 한다. 지금까지 팩은 그 값을 하나도 안 갖고 있었다.

```
팩이 들고 있는 잰 치수 (catalog.bodyDims · source: measured-from-pack)

                        키     선 폭   걸을 때   두께   눈높이
  어른 남자 01        1.810   0.586   0.573   0.388   1.683
  어른 여자 01        1.741   0.469   0.507   0.363   1.606
  정장 남자 01        1.801   0.613   0.594   0.399   1.683
  남자아이 01         1.431   0.498   0.490   0.299   1.330
  합성 기준 팩        1.550   0.460   0.460   0.154   (눈 뼈 없음)
```

**걷는다고 늘 넓어지지는 않는다.** "걸을 때가 더 넓다" 를 계약에 박았다가 남자
팩 넷이 걸렸다 — 선 자세에서 팔이 몸에서 떨어져 있어 그쪽이 더 넓다. 복도를
검토하는 쪽은 둘 중 큰 쪽(`maxWidthM`)을 쓴다.

**눈높이는 눈 뼈가 있는 리그만 적는다.** 합성 기준 팩에는 눈 뼈가 없어서
비워 둔다 — 키 × 0.93 으로 만들지 않는다 (그것이 이 저장소가 처음부터 안
하기로 한 것이다).

이 값은 **사이즈코리아와 다른 것**이다. 저쪽은 모집단 통계이고 이쪽은 이 몸
하나를 잰 것이라, 출처를 `measured-from-pack` 으로 못 박고 게이트가 그것을
지킨다:

```
"이 사람이 이 문을 지나가는가"      → 팩의 bodyDims (그 몸의 폭)
"한국 성인 95%가 지나가는 문인가"   → lib/anthropometry.mjs (통계의 95 백분위)
```

### 용도 프로필 — "학교" 가 무엇을 뜻하는가 (`profiles/*.json`)

공간 종류가 정해지면 그 안에 **누가 어떤 비율로** 있는지가 따라 정해진다.
그것은 건물의 사실이 아니라 사람에 관한 통계라, 사이즈코리아 치수를 여기 둔
것과 같은 기준으로 이 저장소가 갖는다.

**비율을 저장하지 않는다.** 발표된 **비(比)**만 적고 백분율은 계산한다 —
저장하면 둘이 갈린다.

```json
"mix": {
  "source": "kess2025",
  "what": "교원 1인당 학생 수 12.1명 (초등학교, 2025년 교육기본통계)",
  "weights": { "student": 12.1, "teacher": 1 }
}
```

```
school-kr · 530명   학생 490명 (92.37%) · 교원 40명 (7.63%)   배역 100%
                    12.1 은 2025년 교육기본통계(교육부·한국교육개발원,
                    2025-08-28)의 초등학교 교원 1인당 학생 수다
```

**적힌 수는 그 수를 인용한 문장에 묶인다.** 게이트를 일부러 깨 보다가
`12.1` 을 `9.0` 으로 바꿔도 아무 데도 안 걸리는 것을 발견했다 — 비율은 비에서
계산되니 늘 앞뒤가 맞고, 배역은 그냥 다르게 나뉜다. 이제 `what` 문장 안에
그 수가 없으면 막는다.

**못 구한 것은 `pending` 으로 남긴다.**

```
nursing-home-kr   mix.pending — 노인복지법 시행규칙 별표 4 의 요양보호사
                  배치 기준이 필요하다. 국가법령정보센터(law.go.kr)가 이
                  기계에서 안 열리고(curl 000), 받아 온 별표 PDF 는 글자가
                  CID 로 들어 있어 못 읽었다 (2026-09-13 확인).
                  검색 요약에 수가 보이지만 2차 자료라 안 적는다.
```

그동안 쓰는 쪽은 **인원을 직접 주면 된다** — 어차피 "이 시설에 몇 명" 은
공간 쪽이 아는 것이다. 비율로 쓰려 하면 막는다.

```js
planCast(nursing, { packs, counts: { resident: 70, carer: 30 } });
// → 100명 중 30명 · coverage 0.30 · missing: resident 70명 (노인 팩 0개)
```

게이트: `scripts/check-profile.mjs` — 비율이 손으로 적혀 있지 않은가, 출처가
아는 것인가(주소·발표일·**이 기계에서 확인한 날**), 비를 흔들면 비율이 따라
움직이는가, 못 구한 프로필로 비율을 쓰려 하면 막는가, 일과·역할과 정말
이어지는가, 시계가 없는가. 다섯 군데를 일부러 깨서 확인했다.

### 일과 — "학교 하루" 를 활동의 차례로 (`routine.mjs`)

층이 하나 더 쌓인다. 활동이 클립에 대해 한 일을 일과가 활동에 대해 한다.

```
클립    walk-forward · sit · talk          팩이 갖고, 잰 값이 붙는다
활동    meeting · goToRoom · evacuate      클립의 차례
일과    officeDay · schoolDay              **활동의 차례**  ← 여기
```

**안 갖는 것이 요점이다.** 일과는 이 저장소가 spacemaker 를 두 벌 만들기
시작하는 자리라, 넷을 못 갖게 했다: 자리(x, z) · **절대 시각** · 방 이름 ·
조용한 대신하기. "수업 45분" 을 여기 한 줄 적는 순간 시간표가 생기고, 그러면
같은 표가 두 벌 생겨 한쪽만 고쳐진다.

시계는 사람이 지키게 두지 않고 **값으로 찾아낸다** — `clockLike()` 가
`09:00`·`9시 30분` 같은 글과 `hour`·`startTime` 같은 키 이름을 찾고, 게이트가
그것을 네 가지로 일부러 넣어 보며 확인한다 (초 단위 `forS: 45` 는 시각이
아니므로 안 걸려야 한다 — 그것도 본다).

```js
import { planRoutine, startRoutine } from 'peoplemaker';

const r = startRoutine(pack.catalog, 'officeDay', { part: 'worker', seed: 7 });
if (r.update(dt)) player.playClip(person, r.clipId);   // 바뀔 때만 다시 세운다

r.activity.cue();   // 안쪽 활동에게 — "문 앞에 닿았다"
r.cue();            // 일과에게     — "수업이 끝났다"
```

**알림이 둘인 것이 이 층의 유일한 새 개념이다.** 층이 둘이니 끝나는 것도
둘이다 — 섞어 쓰면 걷는 사람이 영영 안 도착하거나 수업이 한 클립 만에
끝난다. 게이트가 둘을 갈라 놓고 서로의 자리에서 안 먹히는지 본다.

지금 있는 일과 셋 — 그리고 **둘은 지금 못 돈다**:

| 일과 | 차례 | 여자 01 로 |
|---|---|---|
| `officeDay` 사무실 하루 | 출근 → 근무 ⇄ 회의 → 퇴근 | ok |
| `schoolDay` 학교 하루 | 수업 ⇄ 복도 ⇄ 급식 (학생·교사) | ✗ `meal` |
| `nursingDay` 요양시설 하루 | 거실 ⇄ 방 ⇄ 식당 (재실자·요양보호사) | ✗ `meal` |

**먹는 클립이 하나도 없어서** 식사가 안 되고, 식사가 안 되니 그 하루도 안
돈다. 마시기로 풀면 화면은 멀쩡하고 "급식실 재실 시간" 만 거짓이 된다 —
그래서 없는 채로 두고 `startRoutine` 이 던진다.

그 바람에 활동 게이트의 규칙도 바뀌었다. "활동은 전부 돼야 한다" 로 두었더니
식사를 넣는 순간 막혔는데, 그것은 결함이 아니라 **사실**이다. 이제 되는 것과
안 되는 것을 적어 두고, **둘 중 어느 쪽이 바뀌어도** 게이트가 말한다 (클립이
들어와서 되기 시작해도 알려 준다).

```
활동 8가지 · 여자 01 로 7/8 — 못 하는 것은 meal (eat 클립 0개)
일과 3가지 · 여자 01 로 1/3 — 사무실 하루만 돈다

사무실 하루가 공간에게: door · desk · seat
                        앉을 자리 0.609m · 손잡이 1.065m  (둘 다 팩에서 잰 값)
```

게이트: `scripts/check-routine.mjs` — 여섯 군데를 일부러 깨서 확인했다
(못 도는 하루를 조용히 시작 · 표에 09:00 · until-cue 가 혼자 끝남 · 씨 무시 ·
안 끝나는 회의를 "끝날 때까지" 로 · 앉을 자리를 일과가 지어냄).

### 배역 — 누구를 어느 팩에 세울 것인가 (`catalog.person`)

"양로원 재실자 100명" 을 받으면 누구를 어느 팩으로 세우는가. 지금까지는 그
물음에 답할 수가 없었다 — **팩이 제가 누구인지를 안 갖고 있었다.** `packId`
문자열(`rocketbox-c01`)로 짐작할 수는 있었지만, 짐작은 이 저장소가 안 하기로
한 것이다.

```json
"person": {
  "source": "declared-by-import",
  "ageBand": "child",      // child · youth · adult · older-adult
  "sex": "male",           // male · female · unspecified
  "mobility": "walk",      // walk · cane · walker · wheelchair
  "attire": "casual"       // casual · business · uniform · care-worker
}
```

**이것은 잰 값이 아니라 적은 값이다.** 살을 재서 "이 사람은 청소년이다" 를
알아낼 방법이 없다 — 키 1.7m 인 열일곱 살과 스물일곱 살은 같은 살이다.
그래서 출처를 `declared-*` 로 두어 `bodyDims` 의 `measured-from-pack` 과
갈라 놓는다. 사람이 아닌 팩(검사용 합성 팩)에는 **안 적는다** — 1.55m 짜리
픽스처를 '어른' 이라고 적으면 그 순간 지어낸 값이 하나 는다.

```js
import { planCast, castReport } from 'peoplemaker';

const cast = planCast(profile, { packs: catalogs, count: 100 });
cast.coverage     // **조건에 정확히 맞은** 비율
cast.kindOf(i)    // 사람 번호 → packId (createMixedCrowd 의 kinds 와 붙는다)
cast.missing      // [{ role, want, n, why }]
```

**없는 사람을 조용히 딴 사람으로 채우지 않는다.** 뛰는 클립이 없는 팩에
대피를 안 주는 것과 같은 이유다 — 조용히 채우면 "노인 시설 피난 시간" 자리에
청년들이 들어앉고, 멀리서 보면 그냥 사람들이라 아무도 못 알아챈다.

```
양로원 100명 · 팩 9개

  resident   70명  ageBand=older-adult   ✗ 0개
  wheelchair 12명  mobility=wheelchair   ✗ 0개
  carer      18명  ageBand=adult         → 어른 6팩에 3명씩

  100명 중 18명 · coverage 0.18
```

대신 채우려면 프로필이 **그렇게 적고 왜인지도 적어야 한다**. 그러면 그 수가
`coverage` 와 따로 세어진다 — 학교 200명을 초등 몸으로 대신 채우면 200명이
다 서지만 정확도는 10%(교직원)로 남는다.

```
팩 9개 — child 2 · youth 0 · adult 6 · older-adult 0 · 걷지 않는 몸 0 · 사람 아님 1
```

게이트: `scripts/check-cast.mjs` — 몫을 나눈 합이 시킨 수와 **정확히** 같은가,
조건의 **오타**를 던지는가(`ageband` 는 조건이 없는 것과 같아져 아무나 다
맞는다), 없는 역할을 조용히 채우는가, 대신 채운 것이 `coverage` 에 안
섞이는가, 그리고 **적힌 사람과 잰 몸이 어긋나는가** — 어린이로 적힌 팩의
키가 어른 중앙값(1.771m)보다 크면 막는다. 절대 키로 안 본다: "어린이는 1.5m
아래" 는 모집단 통계이고 출처가 필요하다.

여섯 군데를 일부러 깨서 확인했고, **그중 둘은 검사가 헛돌고 있었다** — 몫
나누기는 모자라는 쪽만 봐서 반올림 구현이 그대로 통과했고, 조건 오타는
`ALLOWED['ageband'].includes` 가 TypeError 로 던지는 바람에 검사가 아니라
우연이 막고 있었다. 둘 다 고쳤다 (넘치는 경우 추가 · 던진 **이유**까지 확인).

### 상위 명령 — 회의하기 · 방으로 가기 · 대피하기

"의자에 앉기" 같은 낱낱의 동작 위에 **활동**이 있다. 그런데 회의는 어디서
하는가? 그 물음이 경계를 가른다.

```
어디서 · 언제 · 누구와 · 어느 길로   →  공간을 아는 쪽 (spacemaker · urbanspace)
그래서 몸이 무엇을 하는가            →  여기
```

회의를 하려면 사람이 앉고, 말하고, 듣고, 서류를 보고, 일어선다. 그 **차례와
규칙**은 공간을 몰라도 정해진다 — 그것이 `src/lib/activity.mjs` 다. 활동은
자리(x, z)를 하나도 안 만든다. 내는 것은 셋이다:

```js
import { planActivity, startActivity } from 'peoplemaker';

// 1. 이 팩으로 이 활동을 할 수 있는가 — **없으면 무엇이 없는지 말한다**
const plan = planActivity(pack.catalog, 'evacuate');
//    { ok, clips, needs: ['door'], seat: { hipHeightM: 0.61, … }, missing: [] }
//    needs 는 공간에게 달라는 것(앉을 자리·문·책상)이고,
//    seat 은 지어낸 값이 아니라 그 팩의 앉는 클립에서 **잰** 값이다.

// 2. 사람 하나에게 활동을 시킨다 — 자리는 부르는 쪽이 정한다
const act = startActivity(pack.catalog, 'meeting', { part: 'listener', seed: 7 });
if (act.update(dt)) player.playClip(person, act.clipId);   // 바뀔 때만 다시 세운다

// 3. 길이는 공간 쪽이 안다 — 걷는 상태는 **알려 줄 때까지** 안 끝난다
if (arrivedAtDoor) act.cue();
```

지금 있는 활동 넷:

| 활동 | 차례 | 공간에게 |
|---|---|---|
| `meeting` 회의 | 앉기 → 말하기 ⇄ 듣기 ⇄ 서류 (발표자·듣는 사람 따로) | 앉을 자리 |
| `deskWork` 책상에서 일하기 | 앉기 → 일하기 ⇄ 서류·마시기·기지개·통화 | 책상 |
| `goToRoom` 방으로 가기 | 걷기 → 문 열기 → 들어가기 → 둘러보기 | 문 (손잡이 높이까지) |
| `evacuate` 대피 | 둘러보기 → 일어서기 → 뛰기 ⇄ 줄서기 → 문 → 나가기 | 문 (손잡이 높이까지) |

**활동은 클립 id 를 직접 대지 않는다.** 역할(`run` · `sit` · `papers` …)로
말하고, 팩을 받아 그 팩에 있는 것으로 푼다 — 여자 01 에 전화 통화가 없으면
휴대폰으로 물러선다. 없으면 **없다고 말한다**:

```
뛰는 클립이 없는 팩에 대피를 시키면 → ok: false · missing: [run]
                                      startActivity 는 던진다
```

걷는 대피를 조용히 내주면 피난 시간이 거짓이 되기 때문이다. 게이트가 뛰기를
뺀 팩으로 그것을 매번 확인한다 (`scripts/check-activity.mjs`).

### 동작 열여덟 가지 — 그리고 쪼그린 사람은 앉은 것이 아니다

사람마다 동작이 18~19개다. 건물 안에서 사람이 하는 것 위주로 골랐다:

```
걷기 · 서기 · 말하기 · 듣기 · 휴대폰 · 전화 통화 · 손 흔들기 · 둘러보기 ·
사진 · 앉아 있기 · 책상에 앉아 있기 · 문 열기 · 문 두드리기 · 쪼그려 앉기 ·
서류 보기 · 마시기 · 박수 · 책상에서 일하기 · 기지개
```

문과 앉기는 계약이 처음부터 이름을 대 둔 것들이다 ("접촉 이벤트는 앉기·문
열기를 공간에 맞출 때 쓴다").

쪼그리기를 받고 나서 **앉기를 재는 규칙이 틀렸다는 것**이 드러났다. 엉덩이
높이만 보면 쪼그린 사람도 앉은 사람이다 — 그러면 공간 쪽이 거기에 의자를
놓는다. 가르는 것은 **발**이다:

```
발이 엉덩이보다 얼마나 앞에 있는가 (Rocketbox 여자 01)

  앉기 0.554m · 책상에 앉기 0.566m
  쪼그리기 0.075m
  서기 0.107m · 걷기 0.088m
```

그래서 `seat` 은 엉덩이가 낮고(쉬는 자세의 0.8 아래) **발이 0.25m 넘게 앞에
있을 때만** 붙는다. 쪼그리기는 그 사실을 잰 값 대신 note 로 남긴다.

### 손이 닿는 자리 — 손잡이를 어디에 둘 것인가

계약에 `hand-l·hand-r` 와 `touch·release` 가 **선언만 돼 있고 아무도 안
만들고 있었다.** 문 클립이 생겼으니 채운다.

```
clip.reach (재는 값)

  part       어느 손인가
  atS·releaseS  닿는 순간과 떼는 순간 (contacts 에도 같이 들어간다)
  forwardM   엉덩이보다 얼마나 앞인가
  heightM    그때 손이 있는 높이 ← **손잡이를 둘 자리**

  어른 남자 1.108m · 어른 여자 1.065m · 어린이 0.871~0.878m
  (문 두드리기는 더 높다: 1.40~1.49m · 어린이 1.11~1.22m)
```

어린이의 손이 어른보다 **20cm 아래**에서 문을 만난다. 그 수가 팩에 남는다.

**무엇에 닿는지는 안 정한다.** 손이 앞으로 나간 것만으로는 문을 잡았는지
알 수 없다 — 재 보니 책상에 기대기(0.48m)와 손 흔들기(0.41m)가 문 열기
(0.36m)보다 멀리 갔다. 그래서 **그 동작이 무엇인지는 사람이 적고**
(`tags: ['door','reach']`), **언제 어디까지 뻗는지는 우리가 잰다.**

닿는 구간은 발의 디딤과 같은 규약으로 찾는다 — "닿아 있는 상태" 가 아니라
**닿는 사건**이다. 다만 발에는 땅이라는 고정된 높이가 있고 손에는 없어서,
그 클립 **자신의 최고치**(90%)에 견준다.

활동이 그 값을 그대로 넘긴다:

```js
planActivity(pack.catalog, 'evacuate').door
//  { clipId: 'door-open', part: 'hand-r', heightM: 1.108, forwardM: 0.446, … }
```

### 앉은 사람 — 의자 높이를 잰다

계약은 처음부터 "접촉 이벤트는 **앉기**·문 열기를 공간에 맞출 때 쓴다" 고
적어 두었는데, 정작 앉은 클립이 없었다. Rocketbox 의 의자 동작을 받아 팩마다
`sit` 을 넣고, 잰 값에 `seat` 를 더했다.

```
클립의 seat (재는 값 — 사람이 못 적는다)

  hipHeightM     앉았을 때 엉덩이 뼈 높이 (m)
  hipRatio       그 높이 ÷ 쉬는 자세의 엉덩이 높이
  feetForwardM   발이 엉덩이보다 얼마나 앞에 있는가 — 쪼그리기와 가른다
  groundOffsetM  이 클립에서 발이 가장 낮게 간 곳 — 놓는 쪽이 얼마나 올릴지
  dwell          그 높이에 머문 시간의 비율

  어른 여자 0.610m · 어른 남자 0.591m · 남자아이 0.467m · 여자아이 0.500m
  넷 다 쉬는 자세의 0.66 · 발은 바닥(0.000 ~ -0.005m)
```

의자 **면**의 높이는 이 값보다 엉덩이 살 두께만큼 아래인데, 그 두께는 아직
안 잰 값이다 (앉은키·앉은 눈높이와 함께 pending). 그래서 이 저장소는 잰
것까지만 적고, 어느 의자에 앉힐지는 공간을 아는 쪽이 정한다.

**앉기는 접붙이면 안 된다.** 이 파일들은 **쉬는 자세부터 앉아 있어서**,
트랙이 안 건드리는 뼈가 몸의 선 자세로 남는다 — 엉덩이는 앉았는데 발끝이
12cm 땅속으로 들어간 사람이 나왔다. 옮겨 붙이면 짝지은 뼈 전부의 세계 회전을
다시 쓰므로 발이 바닥에 선다.

그 과정에서 옮기기가 **크기를 잘못 재고 있었다는 것**이 드러났다. 엉덩이
높이 비로 쟀는데, 앉은 파일에서는 그 값이 1.51배(어린이에게는 2.75배)가
된다 — 앉아 있으니 엉덩이가 낮고, 그것을 "이 몸이 더 크다" 로 읽는다. 그 비로
옮기니 **앉은 사람이 선 키로 떠올랐다** (엉덩이 92cm · 발끝 32cm). 이제 크기는
**뼈 길이**로 재고(자세로 안 변한다), 세로 자리는 **바닥에서** 잡는다.

게이트: `check-build` 는 픽스처의 앉는 깊이를 흔들어 잰 값이 따라오는지
보고(0.5m 내려가면 0.40m · 0.1m 는 앉은 것으로 안 센다), **적힌 것과 잰 것**이
맞는지 본다 (tags 에 `seated` 인데 엉덩이가 안 내려가면 막는다).
`check-retarget` 은 쉬는 자세가 앉아 있는 원본을 하나 만들어, 옮긴 뒤 엉덩이가
선 자세로 돌아가면 막는다.

### 어린이 — 어른 동작을 그냥 붙이면 안 된다

Rocketbox 의 동작 326개는 전부 어른 리그(`Bip01 …`)로 만들어져 있다. 어린이
몸은 `Bip02 …` 이고 키가 1.43m 다 (어른 1.74~1.82m).

받아 보니 조용히 틀리는 자리가 셋이었다:

1. **트랙이 하나도 안 붙었다** — 이름이 `Bip01` 과 `Bip02` 로 달라서 105개가
   전부 건너뛰어졌다. 3ds Max 는 장면마다 바이페드에 번호를 매긴다. 번호를
   떼면 84개 중 83개가 맞는다 (남는 하나는 뼈가 아니라 메시다). 우리 `biped`
   규약도 `Bip01` 을 박아 두고 있어서 같이 고쳤다.
2. **어린이에게는 `_opacity` 텍스처가 없다** (속눈썹·머리카락 카드가 없는 몸).
   없으면 없는 대로 간다 — 1×1 자리표시를 지어내지 않는다.
3. **붙이고 나니 아이가 어른 크기로 늘어났다.** Biped 동작은 회전만이 아니라
   뼈마다 **자리(translation)** 도 싣는다. 그래서 뼈 길이가 어른 것으로 덮여
   키 1.433m 가 1.740m 가 됐다 (+21.4%). 화면에서는 그냥 걷는 사람이라
   아무도 못 알아챈다.

셋째는 **옮겨 붙여야**(retarget) 한다 — 뼈 길이는 대상 몸의 것을 지키고, 몸
전체의 이동만 엉덩이 높이 비로 줄인다. 수입 스크립트가 스스로 고른다:

```
엉덩이 높이 비 (동작 리그 ÷ 이 몸)

  어른     0.997 ~ 1.007   → 그대로 접붙인다
  어린이   0.788 · 0.826   → 옮겨 붙인다 (문턱 2%)
```

옮겨 붙인 뒤: 키 1.433m → **1.434m (+0.1%)** · 걸음 0.80m/s (어른 1.21m/s) ·
발이 땅에 닿는다(접촉 2회). 옮겼다는 사실은 `sources.json` 에 남는다 —
라이선스는 안 바뀌지만 어떤 비로 줄였는지는 나중에 아무도 못 알아낸다.

**게이트가 이것을 수로 잡는다** (`check-build`): 클립을 틀었을 때 **뼈 길이가
그대로인가**. 살의 경계상자로 재려다 손 흔들기가 8%, 앉기가 −19% 로 걸렸다 —
그것은 몸 크기가 아니라 자세의 크기다. 지금은 이동 트랙만 보고, 멀쩡한 클립을
1.25배로 늘려 놓고 걸리는지도 함께 본다 (3% → 99%).

### 동작 옮기기 (retarget)

동작 하나를 다른 몸으로 옮겨 그 팩의 클립으로 넣는다. 뼈 이름·국소 축·
비율·쉬는 자세(T/A)·앞이 달라도 **뼈가 가리키는 방향**을 맞추고, 몸 전체의
이동은 엉덩이 높이 비로 줄이거나 늘린다. 뼈 길이는 대상 몸의 것을 지킨다.

```sh
# 여자 01 에게 없는 전화 통화를 남자 01 에게서
node scripts/retarget.mjs packs/rocketbox-m01/clips/phone-call.glb rocketbox-f01 phone-call \
     --ko "전화 통화 (여자 01)" --en "Phone call (woman 01)"
```

지금 아는 규약은 `biped`(Rocketbox)·`mixamo` 다. 원본이 팩 밖의 파일이면
`--license` 와 `--tool` 을 줘야 한다 — 옮겼다고 라이선스가 바뀌지는 않는다.
게이트: `scripts/check-retarget.mjs`.

### 방향

`headingRad` 는 **세계에서 바라보는 쪽**이다 (0 = +Z, 시계 반대). 리그가
어느 쪽을 보고 있는지는 팩이 **재서** 갖고 있고(`catalog.forwardRad`),
어댑터가 그 차이를 흡수한다 — 쓰는 쪽은 리그의 사정을 알 필요가 없다.

이것을 안 재던 때 사람들이 시킨 것의 정반대로 걸었다. 걷는 그림은 멀쩡해서
화면만 봐서는 한참 못 알아챈다. 지금은 게이트가 네 방향으로 걸려 보고
**실제로 간 방향**을 재서 견준다.
